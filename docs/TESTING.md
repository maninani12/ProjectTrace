# Validation and test scope

Current enterprise hardening evidence is in [ENTERPRISE_TRUST_VALIDATION.md](../ENTERPRISE_TRUST_VALIDATION.md) and `benchmarks/enterprise-hardening-verification.json`. The fresh local backend run passed 306 tests; frontend passed 24 checks and built 41 public routes / 34 Guide topics. New controlled tests cover structural finding lineage, profiles/coverage, deeper IaC, OIDC/GHES lifecycle, encrypted inventories, streaming, fair queue fencing/recovery, paged graph, checkpoints and private recovery/rotation. `hardening.spec.ts` exercises captured Engineering Changes, component correction persistence, historical coverage and graph pagination against the actual API. The versioned sections below describe historical validation; earlier runtime evidence does not qualify the current hardening candidate on production services.

Run backend checks with `python -m pytest -q`. On hosts with inaccessible system pytest temporary roots, set `PYTEST_DEBUG_TEMPROOT` to a private writable workspace directory. Run browser checks against an isolated API/database, with `PROJECTTRACE_BASE_URL` for the development UI and `PROJECTTRACE_STATIC_BASE_URL` for a production preview; otherwise the production HTML check is explicitly skipped. Never seed/reset a customer database for tests. Imported customer source stays inert.

The backend suite expects `APP_ENV=demo`, synchronous jobs and allowed test origins on both `http://127.0.0.1:5173` and `http://127.0.0.1:5181` (the development defaults include both). In a dedicated test terminal, set `SOURCE_BLOB_DIR`, `SOURCE_UPLOAD_DIR` and `ANALYSIS_KEY_FILE` to private test-only locations. This keeps owned fixture ciphertext and test keys separate from a running workspace. Do not substitute production credentials or source storage.

Backend pytest fixtures create isolated temporary SQLite databases. Deployment uses Alembic; test-only metadata creation is not a production startup dependency. Migration tests separately run a fresh upgrade, rollback and re-upgrade, including provider uniqueness.

Tests cover demo evidence provenance and status transitions, imports vs runtime proof, compound claims, safe SQL, static security rules, no code execution, ZIP traversal/symlinks/limits, prompt injection, tenant/ACL/RBAC/CSRF/IDOR, session logout, secret redaction, review concurrency/audit, idempotent analyses, webhook signature/replay, exception expiry, grounded/unsupported questions, fake citations and incremental content reuse. GitHub tests use mocks and do not count as live provider verification.

Vitest/React Testing Library cover status text, login semantics and actionable login errors. Playwright covers the desktop CEO/developer flow, confirmation review and audit, claim filtering, source inspection, PR gate, all major pages, console exceptions, width overflow, mobile navigation and unsupported investigation. These are critical smoke workflows, not exhaustive frontend coverage.

Historical pre-hardening runs of `scripts/benchmark.py` record repeated static-analysis timings, and `scripts/api_benchmark.py` records a bounded four-client localhost workload. Earlier PostgreSQL migration/query, Redis outage/retry, Linux prefork and forced-crash evidence remains archived; those services were unavailable for current hardening acceptance. Current owned scale and controlled queue measurements are in `LARGE_REPOSITORY_BENCHMARK.md` and `PR_LOAD_BENCHMARK.md`. Sustained production load, saturation/fairness, provider outages, representative customer monorepos and production restore remain unverified. The native benchmark command is `python -m scripts.benchmark_analyzers --output <absolute-output.json>`; its synthetic labels do not estimate real-world precision.

The selected dependency lockfiles are audited with pip-audit/npm audit. Audits are time-specific and do not certify future vulnerability status. `benchmarks/expected-findings.md` documents the safe corpus.

Current test counts, failures resolved during development, browser screenshots, benchmark confusion labels and real-runtime results are recorded in [FINAL_PRODUCT_VALIDATION.md](../FINAL_PRODUCT_VALIDATION.md).
