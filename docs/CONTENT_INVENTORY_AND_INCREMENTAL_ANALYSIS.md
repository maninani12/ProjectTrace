# Source inventories and parser observation reuse

The new ZIP import path uses encrypted seekable upload chunks and tenant-scoped encrypted content blobs. The former 1,000-file / 10 MB small-input routes remain bounded for compatibility. Larger imports use separately configured `REPOSITORY_MAX_FILES`, `REPOSITORY_MAX_BYTES` and `REPOSITORY_MAX_ARCHIVE_BYTES`; quota admission is not a performance guarantee. Per-file native parser intake remains 512 KB. Oversized/non-UTF-8 files retain metadata and unknown LOC where appropriate; unsupported languages are not declared safe.

Inventories and snapshot references are authorized by organization and repository. Blob paths hash the tenant identifier and content. SHA-256 content checks and Fernet authentication protect retained plaintext; source and temporary archives reach disk as ciphertext. The operator must retain encryption keys separately from a matching database/blob backup. Existing redacted source fields are preserved for legacy snapshots; new evidence uses encrypted redacted blob references. Local recovery and key rotation have controlled validation. Automatic snapshot retention/GC and managed production restore qualification remain unfinished; see PRIVATE_DEPLOYMENT_GUIDE.md.

The parser cache key includes tenant, raw content hash, semantic repository path, parser signature, rule version and applicable infrastructure settings. A path is needed because filename/location affects test context, imports, rules and configuration semantics. Cache artifacts contain redacted observations, not a raw source dictionary. Changed files, new versions and changed applicable infrastructure policy trigger fresh parsing; failed parser observations are never reused. Quality threshold/profile changes reuse compatible parser metrics and recompute the gate. Global verifier, dependency, duplication and impact work is not assumed constant-time; it can increase with repository metadata even when only eight source files change.

Partitions are bounded at 100 files / 2 MB. Global correlation still sees observations across all partitions. Missing-policy decisions use the entire captured infrastructure inventory. Native parsing, static semantics, bounded duplicate work and claim limits retain their existing explicit limitations. The benchmark reports actual pipeline/database costs rather than extrapolating from a smaller intake.

## Component boundaries

Package `name` declarations establish static boundaries. A root `.projecttrace/components.json` may contain `{"version":1,"components":[{"root":"services/payments","name":"Payments"}]}`. It is inert JSON; no program/configuration hooks run. Roots must be relative, unique and traversal-free; a maximum of 500 explicit boundaries is accepted. Bare folder names never establish component identity. The longest matching declared boundary applies; explicit ProjectTrace declarations override a manifest at the same boundary, and versioned administrator assignments override both at the same boundary. This is declared scope rather than dynamic workspace/runtime proof.

Authorized administrators edit future component assignments through Settings → Native rule profiles → Repository component boundaries after selecting a repository. Prior inventories retain the captured assignments. API clients use scoped GET/POST `/api/repositories/{id}/components`, submitting the currently returned version. Existing history, graph references and repository root assignment remain present.
