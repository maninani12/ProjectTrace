# Enterprise identity and SCM configuration

## OIDC: implemented, controlled validation; live provider validation unavailable

Deployment operators configure one standards-compliant issuer per deployment using `OIDC_ISSUER`, `OIDC_AUTHORIZATION_URL`, `OIDC_TOKEN_URL`, `OIDC_JWKS_URL`, `OIDC_CLIENT_ID`, `OIDC_REDIRECT_URI`, `OIDC_FRONTEND_URL` and optional `OIDC_CLIENT_SECRET`. The exact callback is `/api/auth/oidc/callback`; the frontend must be an approved application origin. Production requires HTTPS. `OIDC_ALLOWED_HOSTS` constrains outbound hosts; `OIDC_ALLOWED_PRIVATE_CIDRS` explicitly authorizes narrow internal address ranges and `OIDC_CA_BUNDLE_FILE` selects private TLS trust. `OIDC_PRIVATE_HOSTS` alone no longer authorizes private addresses. The validated TCP address is pinned while TLS verifies the original hostname; mixed unsafe DNS results, redirects, proxies, loopback and metadata addresses fail closed. Do not disable TLS. Network policy must additionally enforce approved endpoints and DNS controls; full deployment isolation remains unverified. Secrets belong in the operator's secret manager/environment, never a repository or the product database.

The flow uses Authorization Code, S256 PKCE, browser-bound state, nonce, RS256/ES256 JWKS validation, exact issuer/audience/authorized party, required time claims with 30-second skew, a short login age, bounded responses and one-use state consumed before token exchange. Changing endpoints or organization provider policy invalidates a bound pending attempt. Successful login rotates the local session; logout revokes the ProjectTrace session and clears its cookie. IdP-wide logout is not implemented. Tokens and authorization codes are not stored in audit records; access logging redacts callback query strings.

In Settings → Organization SSO, administrators create a versioned organization provider policy, exact subject membership, or controlled provisioning. Provisioning requires a selected organization, an explicitly mapped signed group and `email_verified=true`. An existing email is never silently linked; an administrator must bind the exact issuer/subject. Newly provisioned accounts have local password login disabled. Email domains never grant roles. Group administrator mapping requires explicit organization-owner authorization; ORG_OWNER cannot be provisioned from groups. Repository grants in a mapping must be explicit and authorized in the organization. Previously granted repository access remains an explicit grant and requires separate revocation; continuous external directory synchronization is not implemented.

Configure group claims on the IdP; missing/overage/dynamic group resolution is not fetched. Select “Require a mapped group for every login” when access depends on current group claims. Group changes are evaluated at login, not continuously against the IdP. Provider policy changes revoke provider sessions. Disabling or removing the provider blocks logins and existing sessions while retaining its audit record. Disabled users cannot use local or OIDC sessions. A separate local organization owner can serve as break-glass access; manage that credential outside the product and restrict it operationally. Multi-issuer discovery, automatic directory synchronization and external account lifecycle webhooks are not implemented.

Controlled tests cover provisioning, verified-email/group rejection, email-collision refusal, stale provider versions, repository scope, disabled users, provider removal and pending-state invalidation. Existing signature/issuer/audience/expiry/nonce/PKCE/replay tests remain required in final regression. Eight new lifecycle checks and the existing flow plus two migration checks passed. Microsoft Entra ID, Okta and Google Workspace have **no live validation evidence** here; they require operator-configured ID-token claims, registered redirect URI, signing keys and an approved tenant. No vendor production-compatibility claim is made from generic fixtures.

## GitHub Enterprise Server

Implemented with controlled fixture validation; live private GHES validation is unavailable. In Settings → GitHub and Enterprise Server connections, administrators save provider type, web/API URL, App/installation ID, API version and operator-owned `ENV:SCM_…` references. Values of those references remain outside the product database. Configure the key environment variable with the PEM key, webhook variable with the signing secret and optional CA variable with the trusted CA file path. Custom CA adds an explicitly selected trust root; TLS verification is never disabled.

GitHub.com uses its canonical origins; GHES requires matching web/API host and an API base ending in `/api/v3`, consistent with [GitHub's installation authentication documentation](https://docs.github.com/en/enterprise-server%403.22/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation). Operators set `GHES_ALLOWED_HOSTS` and narrowly scoped `GHES_ALLOWED_PRIVATE_CIDRS` where internal address access is required. All resolved addresses must pass policy. The TCP socket uses the validated address while TLS verifies the original hostname, preventing a second DNS lookup from changing the socket target. Loopback, link-local and metadata addresses are refused. Redirects, arbitrary payload URLs, Unix sockets and environment proxies are disabled. Outbound network policy remains necessary for deployment defense in depth.

Discover authorized installation repositories, then explicitly connect one. Installation tokens are freshly issued per operation; they are not stored in database records or audit logs. The connector preserves the enterprise API prefix for token, discovery, tree/blob and Checks requests. Checks remain advisory/neutral and publish only system policy names and result states, subject to the separate tenant metadata-egress policy. Repository identities are scoped to the configured provider URL; connected identities cannot be reassigned to another host or installation.

Use `/api/github/webhook/<connection-id>` as the per-connection webhook URL. The signature, installation and connected repository are verified. Delivery IDs are namespaced by connection. Push/PR events retain explicit commits; unsupported fork heads are partial rather than silently fetched outside installation scope. Installation removal/suspension disables the connection; removed repository permissions revoke the corresponding mapping. Workers recheck revocation around provider fetch and publication. Legacy operator-configured GitHub.com endpoints remain available.

Validation: eleven new GHES/network/configuration/workflow checks plus four existing connector checks passed (15 total). These use controlled transports and isolated databases; they establish no live server, private CA deployment, vendor version, throughput or production compatibility claim. Installation discovery remains bounded to 100 repositories in this increment. Bounded tree/blob streaming and encrypted incremental inventory storage are implemented and covered by controlled tests; successful scale measurements are separate reports, not live GHES qualification.
