# GitHub App integration

Use a GitHub App with Metadata:read, Contents:read and Pull requests:read. Request Checks:write only if checks are explicitly enabled. Do not request source writes. Subscribe to push and pull_request events as needed.

Configure GITHUB_APP_ID, GITHUB_PRIVATE_KEY (PEM), GITHUB_INSTALLATION_ID and GITHUB_WEBHOOK_SECRET through secure environment injection. The .env.example is a reference: the native application does not automatically load .env files. With a signed-in administrator and CSRF header, POST /api/github/connect with {repository_id, system, owner, checks_enabled:false}. It tests installation access and grants the initiating user access to the chosen repository. Other users need their own source grants; provider permission inheritance/member synchronization is still a production gate.

POST /api/github/webhook verifies HMAC-SHA256 and persists delivery uniqueness. Configure JOB_MODE=celery and Redis to dispatch provider jobs. Receipt, source analysis and check publication are distinct states. Jobs with failed broker dispatch remain durable and can be retried through /api/jobs/{id}/retry; queued/stopped jobs can be cancelled. There is no production outbox dispatcher or full distributed backpressure yet.

The inventory worker fetches bounded GitHub trees/blobs using temporary installation tokens and walks truncated recursive trees through bounded subtree requests. Symbolic links and submodules are explicit `UNSUPPORTED` inventory entries: their targets are never fetched or followed. Oversized files become `SKIPPED_SIZE_LIMIT`; whole-repository file/byte/metadata limits still reject intake. Complete large GitHub.com trees use read-only GraphQL blob batches capped at 100 paths and 2 MB of declared source per request, with verified REST fallback for binary/truncated or transcoded text. Received bytes must match both the exact-commit tree's declared size and Git blob SHA. GHES and smaller trees retain the REST stream. The legacy bounded `fetch_snapshot` adapter still rejects links/truncation/oversize data. No customer repository commands are executed. Owner/repository and SHA formats are validated; arbitrary URLs are never accepted. Fork source permissions, large-installation pagination, sustained load and real check publication require live tests.

Historical validation before the 2026-10-08 per-connection regression check: the test environment had no GitHub App credentials or installation, so live end-to-end behavior was not verified. Mocks verified selected transport contracts only. This earlier note does not describe the current credentialed local instance.

Provider contracts were checked against the official [Git trees documentation](https://docs.github.com/en/rest/git/trees) and [check-run documentation](https://docs.github.com/en/rest/checks/runs). Those documentation checks used no live credentials.

The current per-connection endpoint is `/api/github/webhook/{connection_id}`. Its signed ping regression, local credentialed checks, active tunnel check, and remaining source-ingestion requirements are recorded in [the 2026-10-08 validation report](GITHUB_WEBHOOK_REGRESSION_VALIDATION.md). A successful ping does not capture source or start analysis.

The subsequent [real OpenMetadata recovery report](OPENMETADATA_REAL_WORLD_VALIDATION.md) records live source diagnostics, worker recovery, ZIP rejection, fixes and current authentication/configuration blockers. The repository card exposes the existing protected retry endpoint for retryable jobs in Celery mode. Retry requires the owning account's normal session, CSRF and repository authorization; a demo session cannot recover another tenant's job. `recover_jobs` redispatches stranded queued jobs and handles expired leases; it does not reset terminal failed jobs.
