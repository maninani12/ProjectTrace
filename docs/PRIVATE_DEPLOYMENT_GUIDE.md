# Private deployment candidate

ProjectTrace uses one application core for local and private deployments. `infrastructure/kubernetes` is an operator template for external PostgreSQL, Redis, S3-compatible storage, OIDC and SCM. It is **not a tested production installation**. Docker, Kubernetes and approved managed-service credentials were unavailable here. Controlled application, storage, migration, rotation and local recovery tests do not substitute for a staging acceptance run.

## Install prerequisites

Use an approved cluster/CNI that enforces NetworkPolicy and the restricted Pod Security Standard. Provide a TLS ingress controller, private DNS, a managed secret delivery mechanism, verified PostgreSQL and Redis TLS, and a versioned private object bucket. Define administrator ownership, alert destinations, backup retention and measured RPO/RTO before promotion. Application-managed PostgreSQL RLS and automatic external WORM audit archival are not implemented.

Render an operator overlay from `infrastructure/kubernetes/kustomization.yaml`. Replace every `example.invalid` origin/endpoint and every `operator-pinned` image. Configure exact managed dependency CIDRs/ports, the ingress controller's namespace/labels and any explicitly authorized IdP/GHES endpoints. The supplied base denies all external ingress and egress, allowing only same-namespace traffic and cluster DNS. It deliberately cannot connect to external dependencies until the operator supplies the narrow network rules. Do not substitute unrestricted Internet egress. A NetworkPolicy manifest existing on disk does not prove enforcement by the cluster.

Build the backend with a verified `PYTHON_IMAGE` digest and the frontend with verified `NODE_IMAGE` and `NGINX_IMAGE` digests. Docker build arguments support these pins; development defaults remain mutable tags. Scan the resulting OCI images, record resolved digests, emit an SBOM and sign/attest the build in your approved registry pipeline. Set those verified release digests in the operator overlay. No fabricated image digests, image signatures or clean container-scan claims are supplied.

## Managed secrets and TLS

Create `projecttrace-managed` using your secret manager/External Secrets/CSI mechanism. Never commit a Secret containing credentials. The base mounts files for `DATABASE_URL`, `REDIS_URL`, `ANALYSIS_INPUT_KEY`, `AUDIT_CHECKPOINT_KEY`, `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY`; mount CA certificates as required. The process loads only allowlisted `*_FILE` variables, bounds files to 32 KB, and rejects conflicting environment values. SDK workload identity can replace static S3 credentials through an operator overlay with projected tokens and required STS egress. The base does not grant an automatic Kubernetes service-account token.

Use `postgresql+psycopg://…?sslmode=verify-full&sslrootcert=/run/secrets/POSTGRES_CA.pem` and `rediss://…?ssl_cert_reqs=required&ssl_ca_certs=/run/secrets/REDIS_CA.pem`. Encode credential URL components correctly. Production startup requires verified TLS settings, explicit HTTPS origins, a valid Fernet key and Celery. Production disables demo access, public registration and API documentation. Bootstrap an organization owner interactively with `python -m scripts.admin`; passwords are not logged and existing users are not overwritten. Configure OIDC provisioning/grants and monitored break-glass access using `OIDC_AND_GHES_CONFIGURATION.md`.

## Encrypted source storage

`SOURCE_BLOB_BACKEND=s3` uses the configured HTTPS `SOURCE_S3_ENDPOINT`, approved host, bucket, region and optional CA file. Tenant-separated keys contain tenant SHA-256/content digest, never raw paths. Only Fernet-authenticated ciphertext is sent; reads are bounded and validate the plaintext digest after decrypting in memory. `SOURCE_S3_KMS_KEY_ID` requests SSE-KMS; otherwise the adapter requests server-side AES256 encryption. The Fernet application key still needs separate secret-manager protection: SSE-KMS is not automatic KMS wrapping of that key. An S3 SDK response is not proof of bucket encryption/IAM/retention policy enforcement. Use bucket policies, private endpoints, versioning, server encryption and least-privilege prefix access, then verify them in staging.

S3 transport verifies TLS, disables inherited proxies, bounds time/retries and rejects requests escaping the configured endpoint. DNS/socket pinning is implemented for OIDC/GHES, not this SDK adapter; enforce S3 destination/DNS controls at the deployment network. Changing an existing local installation to S3 requires an offline, hash-verified migration of every recorded ciphertext blob; changing the setting alone does not move historical content.

API source-upload spools are encrypted temporary chunks on bounded scratch storage. API and worker local-mode deployments must share `source-data`; the development Compose path now does so. Private S3 mode shares content through the object store and metadata through PostgreSQL. Source retention follows retained snapshots; no automatic customer snapshot/history deletion occurs. Expiring queued inputs are purged after 72 hours. Object lifecycle rules must preserve every referenced current and historical blob; automatic snapshot retention/GC remains a limitation.

## Workers, readiness and operations

The template provides two API replicas, native/SCM/advisory workers, a separately bounded large-analysis worker, one scheduler and a non-retrying migration Job. All run without root, privilege escalation or writable image filesystems, with resource ceilings and temporary volumes. Set node-level process limits and approved runtime profiles. Parser helpers additionally enforce CPU/address-space limits on POSIX and CPU/memory Job Object ceilings on Windows; a complete per-helper filesystem/network sandbox remains unverified.

Default global/tenant/repository running ceilings are 4/2/1; pending quotas are 10,000/1,000/200. Configure worker counts together with database ceilings, then measure realistic load. Large-inventory/SCM jobs default to 900 seconds, bounded to 120–3,600; production wall timeouts remain wall timeouts. `/health` reports process health; production `/ready` checks the database, installed migration head and Redis. It does not assert workers are available. Worker readiness probes use a bounded targeted broker ping. Monitor scheduler availability, queue age, expired leases/recoveries, failure rates, API latency, worker RSS, object/DB errors and audit-integrity failures. The API's authorized metrics and structured logs contain IDs/status/durations, not raw source or exception bodies. Central log/metric/alert infrastructure is operator-supplied.

## Upgrade, recovery and rotation

Stop admissions and quiesce workers. Take a transaction-consistent PostgreSQL backup plus matching object versions and external audit checkpoints. Verify restoration into an isolated staging database/bucket with the same schema revision and separately retained application/audit keys. Apply migrations through the one migration Job before rolling out the new API/workers; never run multiple migrators. Run scoped login/import/history/review/gate/graph smoke tests and compare counts/constraints. Migrations 0011/0012 refuse unsafe downgrade while referenced inventories or active claims remain. Rollback may require restoring the matching old database/object snapshot, not dropping new storage tables.

For local SQLite, `python -m scripts.recovery_bundle backup --database <db> --blobs <blob-root> --bundle <fresh-directory> --key-file <protected-key>` validates and copies the DB plus all recorded encrypted blobs. `restore --bundle <bundle> --destination <fresh-directory> --key-file <protected-key>` checks hashes, foreign keys, ciphertext and content identity before creating the restored directory. Bundles exclude keys, refuse overwrite and reject unsafe manifest paths. They contain private data and must never be attached to a source release. Windows access control must be applied by the operator; POSIX modes alone are not proof of a Windows ACL.

For analysis-key rotation, verify backups and stop writers/workers. Set the new `ANALYSIS_INPUT_KEY` and an operator JSON list `ANALYSIS_PREVIOUS_KEYS` containing at most three old keys. Restart all processes with the same key set. `python -m scripts.rotate_analysis_key` previews counts; `--apply` re-encrypts recorded blobs, retained analysis inputs and pending PKCE verifiers without changing content identities. Interrupted rotation is recoverable while old keys remain available. Verify every restored/current source and pending job before removing old keys; retain keys required by retained backup/object versions. Keep audit checkpoint key history separately; automatic audit re-signing/key-history management is not implemented.

Acceptance still required: actual Kubernetes render/admission/run, managed PG/Redis/S3 TLS and failure drills, backup restoration, image vulnerability promotion, signed build provenance, live IdP/GHES interoperability, network enforcement and representative sustained load. No availability, RPO/RTO, SOC2/ISO, zero-false-positive or enterprise-readiness certification is claimed.
